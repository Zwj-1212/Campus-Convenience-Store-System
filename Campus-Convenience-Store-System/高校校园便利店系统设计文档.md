# 高校校园便利店系统项目详细设计文档

---

# 一、项目概述

## 1.1 项目名称

基于 Spring Boot 的高校校园便利店管理系统

## 1.2 项目背景

大学校园里的便利店是学生日常消费的重要场所，品类以零食、饮料、文具为主。校园便利店具有明显的高峰时段特征——下课后和晚自习后结账集中，对收银速度和库存管理提出了较高要求。传统手工记账方式难以应对高峰时段的快速结账需求，也无法及时掌握库存状况。为提高便利店运营效率和管理水平，有必要开发一套校园便利店管理系统，实现进货录入、POS 收银、库存预警和数据统计等功能。

这个场景下，学生消费高峰的特点让系统的库存预警和快速收银功能更有实际意义。

## 1.3 项目目标

本项目采用前后端分离架构，重点实现以下业务模块：

- 供应商管理
- 商品管理
- 进货管理
- POS 销售收银
- 库存管理与预警
- 数据统计（按供应商、商品类别、单品维度）

系统重点体现以下能力：

- 数据库设计能力
- 前后端分离思想
- RESTful API 设计
- Java Web 开发能力
- 进销存业务流转逻辑

# 二、项目技术架构

## 2.1 前端技术

使用技术：HTML5、CSS3、JavaScript、Fetch API

本项目未采用 Vue、React 等前端框架，原因：面向课程设计场景、页面数量较少、便于控制实现成本、便于快速完成开发与联调。

前端主要负责页面展示、用户交互、数据输入、数据渲染和接口调用。POS 收银页面需特别优化交互体验，支持扫码枪快速输入和键盘快捷键操作，以应对下课高峰时段的快速结账需求。

## 2.2 后端技术

使用技术：Java、Spring Boot、JDBC、Maven、Lombok

后端主要负责接收请求、处理业务逻辑、访问数据库并返回 JSON 数据。

## 2.3 数据库技术

使用 MySQL。负责商品数据、进货记录、销售记录、库存信息、预警信息的存储与管理。

## 5.3 Service 层业务规则

**POS 销售**：同一事务内 → 校验每件商品总库存（SUM(inventory.quantity)）是否充足 → 按 FIFO 原则从最早过期批次扣减 inventory.quantity（expiryDate ASC 排序，逐批扣减）→ INSERT sale + INSERT saledetail（多条）→ 若扣减后该商品总库存低于 product.alertMin 则 INSERT stockalert(alertType=1, 缺货预警)。为应对高峰并发，Service 层使用 `SELECT ... FOR UPDATE` 对 inventory 行加锁，防止超卖。

**进货入库**：同一事务内 → INSERT purchase(status=0, 草稿) + INSERT purchasedetail（多条）→ 确认提交后 UPDATE purchase SET status=1 → 按明细逐条 INSERT inventory（每笔进货明细对应一条库存批次记录，记录 detailId 和 expiryDate）→ totalAmount 由 Service 层根据明细自动计算（SUM(purchasePrice × quantity)），保证数据自洽。

**库存预警**：缺货预警在 POS 销售后自动生成（当 SUM(inventory.quantity) < product.alertMin 时）；临期预警由后端定时任务（每天凌晨执行）扫描 inventory 表中 expiryDate 距当前 ≤ 7 天的批次，生成 stockalert(alertType=2, 临期预警)。在首页展示所有 status=0 的未处理预警。

## 5.4 DAO 层示例

```java
public class ProductDao {

    public List<Product> search(String keyword) {
        String sql = "SELECT p.productId, p.productName, p.barcode, p.defaultPrice, "
                   + "c.categoryName, p.status FROM product p "
                   + "LEFT JOIN category c ON p.categoryId = c.categoryId "
                   + "WHERE p.productName LIKE ? OR p.barcode LIKE ?";
        List<Product> products = new ArrayList<>();
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            String like = "%" + keyword + "%";
            ps.setString(1, like);
            ps.setString(2, like);
            try (ResultSet rs = ps.executeQuery()) {
                while (rs.next()) {
                    Product product = new Product();
                    product.setProductId(rs.getInt("productId"));
                    product.setProductName(rs.getString("productName"));
                    product.setBarcode(rs.getString("barcode"));
                    product.setDefaultPrice(rs.getBigDecimal("defaultPrice"));
                    products.add(product);
                }
            }
        }
        return products;
    }

    public int updateInventoryQuantity(int productId, int delta) {
        String sql = "UPDATE inventory SET quantity = quantity + ? WHERE productId = ?";
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setInt(1, delta);
            ps.setInt(2, productId);
            return ps.executeUpdate();
        }
    }
}
```

# 六、数据库设计

> **命名风格**：采用课堂熟悉的 camelCase（`purchase`、`saledetail`、`stockalert`），与课堂风格保持一致。
>
> **核心设计**：product（商品基本信息 + 默认售价）+ inventory（实时库存 + 预警阈值）分离，库存变动由进货和销售驱动；purchase 追踪每一次进货来源；sale 记录每一笔 POS 交易明细。
>
> **自然主键**：product 使用自增 productId，supplier 使用自增 supplierId，purchase 和 sale 使用自增 ID，支持条码 barcode 快速查找。

## 6.3 表关系

```text
supplier (1) ──── (N) purchase (1) ──── (N) purchasedetail (N) ──── (1) product (1) ──── (1) category
                                    │                            │                      │
                                    │                            │                      ├── (N) inventory (批次级，含 expiryDate)
                                    │                            │                      │       │
                                    │                            │                      │       └── (N) stockadjust
                                    │                            │                      │
                                    │                            │                      └── (N) stockalert
                                    │                            │
user (1) ──── (N) purchase         user (1) ──── (N) sale (1) ──── (N) saledetail (N) ──── (1) product
```

核心关系：supplier 与 purchase 一对多；purchase 与 purchasedetail 一对多；purchasedetail 与 inventory 一对多（一批进货对应多条库存批次）；product 与 inventory 一对多（同一商品多个批次）；product 与 stockalert 一对多；inventory 与 stockadjust 一对多；user 与 sale 一对多；sale 与 saledetail 一对多。

## 6.4 设计原则

- product 存商品基本信息、默认售价和预警阈值（alertMin），inventory 按批次存实时库存和过期日期，同一商品可有多条库存批次记录
- 进货确认后按明细逐条 INSERT inventory（关联 detailId 以便追溯），同时自动更新 product.defaultPrice
- 销售时按 FIFO 原则（expiryDate ASC）逐批扣减 inventory.quantity，扣减后总库存低于 alertMin 则自动生成缺货预警
- 密码使用 SHA-256 哈希存储，不存明文
- 状态字段统一数字编码（TINYINT），包括支付方式
- 所有外键建立索引
- barcode 建立唯一索引（允许 NULL），支持扫码枪快速查找
- 销售和进货操作使用事务保证数据一致性；POS 销售使用行级锁（SELECT FOR UPDATE）防止并发超卖
- 本系统暂不处理退货退款与商品报废场景，如需扩展可在 sale 表增加退款标记字段

## 6.5 核心建表 SQL

```sql
CREATE TABLE user (
    userId     INT PRIMARY KEY AUTO_INCREMENT,
    username   VARCHAR(50) NOT NULL UNIQUE,
    password   VARCHAR(64) NOT NULL COMMENT 'SHA-256哈希存储',
    realName   VARCHAR(50) NOT NULL,
    role       TINYINT NOT NULL DEFAULT 1,
```

## 7.3 核心业务规则

**POS 销售**：同一事务内 → 校验每件商品 product.status=1（在售）且 SUM(inventory.quantity) ≥ 购买数量 → 按 FIFO（expiryDate ASC）逐批扣减 inventory.quantity，使用 `SELECT ... FOR UPDATE` 行级锁防并发超卖 → 计算 totalAmount → INSERT sale + INSERT saledetail（多条）→ 若扣减后总库存 < product.alertMin 则 INSERT stockalert(alertType=1, 缺货预警)。

**进货入库**：先 INSERT purchase(status=0, 草稿) + INSERT purchasedetail（多条，totalAmount 由 Service 层按 SUM(purchasePrice × quantity) 自动计算）→ 店员确认后 UPDATE purchase SET status=1 → 按明细逐条 INSERT inventory（每条关联 detailId，记录 expiryDate）→ 若 inventory 中无该商品记录则首次创建。

**库存预警**：缺货预警在 POS 销售后自动生成（当 SUM(inventory.quantity) < product.alertMin 时）；临期预警由后端定时任务（每天凌晨执行）扫描 inventory 表中 expiryDate 距当前 ≤ 7 天的批次，生成 stockalert(alertType=2, 临期预警)。在首页展示所有 status=0 的未处理预警。

**统计查询**：按月（saleTime/purchaseDate 的 YEAR-MONTH）聚合。供应商维度统计该月各供应商送货总金额和总数量；类别维度统计该月各类别商品的销售总额和总销量；单品维度按销量降序排列，展示畅销排行。

**用户管理**：管理员（role=2）可新增店员账号、重置店员密码、查看所有用户。店员（role=1）仅可修改自己的密码。所有用户登录后可进入 POS 收银和进货等日常操作页面。

# 十、项目答辩重点

答辩时重点说明：数据库进销存设计（特别是 inventory 批次级库存与 FIFO 扣减）、前后端分离架构、POS 销售并发控制与事务逻辑、库存预警机制。

重点解释以下 8 张核心表：

| 表 | 作用 |
| ---- | ---- |
| `product` | 商品基本信息（productId 主键，含 defaultPrice 默认售价、alertMin 预警阈值和 barcode 条码） |
| `inventory` | 批次级库存（同一商品可有多条记录，每条关联一个进货批次 detailId，记录该批次 quantity 和 expiryDate） |
| `purchase` | 进货单（supplierId 关联供应商，status 区分草稿/已完成/已取消） |
| `purchasedetail` | 进货明细（每条记录对应一种商品的进货数量/进价/售价/生产日期/过期日期） |
| `sale` | 销售单（userId 关联收银员，记录每笔交易的总额和支付方式） |
| `saledetail` | 销售明细（每条记录对应一种商品的销售数量/单价/小计） |
| `stockalert` | 库存预警（alertType 区分缺货和临期，status 标记是否已处理） |
| `stockadjust` | 盘点调整记录（追踪每次库存手动调整的前后数量和差异原因） |

通过 `status` 字段实现状态流转。POS 销售时使用 `SELECT FOR UPDATE` 行级锁 + FIFO 批次扣减，进货采用草稿-确认两阶段提交，全过程结合事务处理，保证销售记录、批次库存和预警数据同步更新。系统特别针对校园便利店的高峰消费场景，优化了扫码收银的快速响应和库存的实时预警能力。
